# LandIS Full Spatial Warehouse Setup

This guide is for a user who wants to ask spatial LandIS questions through
MCP-Geo, for example "what NATMAP unit is at this point?", "which NSI sites are
near this location?", or "summarize soil constraints across this area".

It assumes the user wants a full spatial warehouse, not just metadata discovery.

## Architecture Decision

Do not create a separate LandIS MCP server for Stephen's first full setup.

Use one MCP-Geo server with a LandIS PostGIS warehouse behind it:

- MCP-Geo is the MCP surface and already exposes the LandIS tools.
- PostGIS is the spatial warehouse and query engine.
- `LANDIS_LOCAL_DATA_ROOT` is the host directory containing the local LandIS
  archive/mirror.
- `scripts/claude-mcp-local` and `scripts/mcp-docker-local` manage the Docker
  topology and pass `LANDIS_WAREHOUSE_DSN` into the app container.

A separate LandIS MCP server is worth considering only if Cranfield needs an
independent release cadence, a separate licence/security boundary, separate
service ownership, or hard performance isolation from OS/ONS/admin tools. Those
are deployment and governance reasons, not a requirement for spatial LandIS
access in this repo.

## What Full Spatial Means

Metadata-only LandIS calls work without PostGIS:

- `landis_catalog_list_products`
- `landis_metadata_get`
- `landis_archive_list_items`
- `landis_archive_get_item`

Full spatial LandIS calls require a populated PostGIS warehouse:

- `landis_natmap_point`
- `landis_natmap_area_summary`
- `landis_natmap_thematic_area_summary`
- `landis_nsi_nearest_sites`
- `landis_nsi_within_area`
- `landis_nsi_profile_summary`
- `landis_soilscapes_point`
- `landis_soilscapes_area_summary`
- `landis_derive_pipe_risk`

An empty PostGIS database is not enough. The `landis.*` tables must exist and
must contain the NATMAP, NSI, Soilscapes, or pipe-risk rows needed by the tool.

## Recommended Path

1. Clone and build MCP-Geo.

   ```bash
   git clone https://github.com/chris-page-gov/mcp-geo.git
   cd mcp-geo
   cp .env.example .env
   docker build -t mcp-geo-server .
   ```

2. Put the LandIS archive under a stable host data root.

   The wrapper defaults to `~/Data`, so this is the least surprising layout on
   macOS:

   ```text
   /Users/steve/Data/
     landis_portal_archive_YYYY-MM-DD/
       data_source/
       ...
     landis_warwickshire_validation/
       soilscapes_warwickshire_normalized.geojson
       official/
         landis_official_pipe_risk_warwickshire.geojson
   ```

   The portal archive should contain the downloaded Feature Service payloads and
   metadata generated by the LandIS archive download process. Keep this raw data
   outside git.

3. Configure only the portable LandIS settings in `.env`.

   ```text
   LANDIS_LOCAL_DATA_ROOT=/Users/steve/Data
   LANDIS_ENABLED=true
   LANDIS_LIVE_ENABLED=true
   MCP_TOOLS_DEFAULT_TOOLSET=starter
   MCP_TOOLS_DEFAULT_INCLUDE_TOOLSETS=core_router,landis_soils
   ```

   Do not set `LANDIS_WAREHOUSE_DSN` for the wrapper-managed setup. The wrapper
   sets it to the PostGIS sidecar DSN inside Docker.

   `ROUTE_GRAPH_DSN` is not a LandIS setting. It is for routing/pgRouting.

4. Check what the wrapper will mount.

   ```bash
   MCP_GEO_DOCKER_PLAN_ONLY=1 ./scripts/claude-mcp-local
   ```

   Confirm that `landis_host_data_root` points at the directory containing the
   LandIS archive and that `landis_mount_enabled=true`.

5. Start through the Claude wrapper for normal use.

   In Claude Desktop, configure the MCP command to the repository wrapper:

   ```text
   /Users/steve/code/mcp-geo/scripts/claude-mcp-local
   ```

   The wrapper starts the PostGIS sidecar, mounts the LandIS data root read-only,
   creates the LandIS schema, and auto-loads missing warehouse tables from the
   mounted archive. The first start can take materially longer than later starts
   because the spatial tables are loaded before the stdio server begins serving
   requests.

## Clean Spatial Validation

For a one-off command-line validation, send a JSON-RPC request into the wrapper.
The wrapper logs status messages on stderr and returns the MCP response on
stdout.

First confirm the catalog is visible:

```bash
REQUEST='{"jsonrpc":"2.0","id":1,"method":"tools/call","params":'\
'{"name":"landis_catalog_list_products","arguments":{"limit":5}}}'
printf '%s\n' "$REQUEST" | ./scripts/claude-mcp-local
```

Then run a spatial NATMAP point lookup:

```bash
REQUEST='{"jsonrpc":"2.0","id":2,"method":"tools/call","params":'\
'{"name":"landis_natmap_point","arguments":{"lat":52.2,"lon":-1.6}}}'
printf '%s\n' "$REQUEST" | ./scripts/claude-mcp-local
```

Run an NSI nearest-sites lookup:

```bash
REQUEST='{"jsonrpc":"2.0","id":3,"method":"tools/call","params":'\
'{"name":"landis_nsi_nearest_sites","arguments":{"lat":52.2,"lon":-1.6,"limit":5}}}'
printf '%s\n' "$REQUEST" | ./scripts/claude-mcp-local
```

Run a thematic NATMAP area summary. Use `landis_catalog_list_products` to check
the callable thematic `productId` values.

```bash
REQUEST='{"jsonrpc":"2.0","id":4,"method":"tools/call","params":'\
'{"name":"landis_natmap_thematic_area_summary","arguments":'\
'{"productId":"natmap-carbon","bbox":[-1.65,52.15,-1.55,52.25]}}}'
printf '%s\n' "$REQUEST" | ./scripts/claude-mcp-local
```

Expected result: `ok:true` or a tool-specific result object with LandIS
provenance/caveats. A `NOT_FOUND` result can still be a healthy system if the
test point is outside coverage for the loaded layer.

## Validate Archive Completeness

The wrapper automatically skips incomplete portal archives. To check an archive
directly, use the local Docker image and mount the data root:

```bash
docker run --rm \
  -v "$HOME/Data:/landis-data:ro" \
  --entrypoint python \
  mcp-geo-server \
  scripts/landis_phase2_ingest.py \
  --dsn postgresql://unused \
  --validate-archive-root \
  --portal-archive-root /landis-data/landis_portal_archive_YYYY-MM-DD
```

The `--dsn` value is not used in validation mode, but the current CLI still
requires the argument.

## Confirm Warehouse Rows

After the first wrapper start, the Claude wrapper uses these default sidecar
names:

- PostGIS container: `mcp-geo-postgis-claude`
- PostGIS volume: `mcp-geo-postgis-claude`
- Docker network: `mcp-geo-claude`

Check the loaded row counts:

```bash
docker exec mcp-geo-postgis-claude \
  psql -U mcp_geo -d mcp_geo \
  -c "select 'product_registry' as table_name, count(*) from landis.product_registry
      union all select 'natmap_polygons', count(*) from landis.natmap_polygons
      union all select 'natmap_thematic_polygons', count(*) from landis.natmap_thematic_polygons
      union all select 'nsi_sites', count(*) from landis.nsi_sites
      union all select 'nsi_observations', count(*) from landis.nsi_observations
      union all select 'soilscapes_polygons', count(*) from landis.soilscapes_polygons
      union all select 'pipe_risk_polygons', count(*) from landis.pipe_risk_polygons;"
```

For the phase-2 archive path, `product_registry`, `natmap_polygons`,
`natmap_thematic_polygons`, `nsi_sites`, and `nsi_observations` should be
non-zero. `soilscapes_polygons` and `pipe_risk_polygons` are non-zero only when
the validation extracts are present under `landis_warwickshire_validation`.

## Repeatable Clean Tests

The wrapper does not reload tables that already have rows. This is intentional
for fast warm starts.

For a clean test without deleting an existing Stephen/Claude volume, use a
fresh sidecar name and volume:

```bash
MCP_GEO_POSTGIS_CONTAINER=mcp-geo-postgis-stephen-clean \
MCP_GEO_POSTGIS_VOLUME=mcp-geo-postgis-stephen-clean \
MCP_GEO_DOCKER_NETWORK=mcp-geo-stephen-clean \
./scripts/claude-mcp-local
```

For a deliberate rebuild of an existing warehouse, stop the MCP client first,
then either run the ingest scripts manually against the sidecar DSN or recreate
the wrapper PostGIS volume. Recreating the volume deletes the loaded warehouse
state, so only do that when the raw LandIS archive remains available.

## Manual External PostGIS Path

Use this path only when Stephen already has a managed PostGIS instance and does
not want the wrapper sidecar.

1. Create a PostGIS database reachable from the app container.
2. Set:

   ```text
   LANDIS_WAREHOUSE_DSN=postgresql://USER:PASSWORD@HOST:5432/DBNAME
   LANDIS_ENABLED=true
   LANDIS_LIVE_ENABLED=true
   ```

3. Load the phase-2 archive:

   ```bash
   python scripts/landis_phase2_ingest.py \
     --dsn "$LANDIS_WAREHOUSE_DSN" \
     --portal-archive-root /absolute/path/to/landis_portal_archive_YYYY-MM-DD
   ```

4. Load any Soilscapes or pipe-risk validation layers:

   ```bash
   python scripts/landis_ingest.py \
     --dsn "$LANDIS_WAREHOUSE_DSN" \
     --soilscapes /absolute/path/to/soilscapes.geojson \
     --pipe-risk /absolute/path/to/pipe-risk.geojson \
     --dataset-version 2026-warwickshire-validation \
     --source-url https://www.landis.org.uk/soilscapes/ \
     --license-name "LandIS validation extract"
   ```

This path needs local Python dependencies for geospatial file formats. The
Docker wrapper avoids that host-Python setup by running the ingest scripts
inside the MCP-Geo image.

## Common Failures

`LIVE_DISABLED` with `landis_warehouse_unconfigured` means no warehouse DSN was
available to the app. Use the wrapper or set `LANDIS_WAREHOUSE_DSN`.

`UPSTREAM_CONNECT_ERROR` means the DSN was present but PostGIS was unreachable
or rejected the connection.

`NOT_FOUND` means the tool ran but did not find coverage for that point or area.
Check whether the coordinate is inside the loaded layer coverage.

Wrapper log `LandIS portal archive not found under ...` means the data root was
mounted, but no `landis_portal_archive_*` directory was found below it.

Wrapper log `Skipping incomplete LandIS portal archive` means the directory
exists but is missing required Feature Service payloads or metadata.

`landis_mount_enabled=false` in plan output means the configured
`LANDIS_LOCAL_DATA_ROOT` path does not exist from the host shell running the
wrapper.
