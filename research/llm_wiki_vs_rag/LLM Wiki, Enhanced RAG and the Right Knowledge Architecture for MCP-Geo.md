# LLM Wiki, Enhanced RAG and the Right Knowledge Architecture for MCP-Geo

## Executive summary

The strongest reading of the evidence is that Karpathy-style LLM Wiki systems are **not a universal replacement for RAG**, but they are a real and important architectural shift for **accumulating knowledge work**. Karpathy’s primary sources describe a pattern in which immutable raw sources are compiled into an LLM-maintained markdown wiki with a schema file, index, log, and recurring maintenance operations. The central claim is not simply “better retrieval”, but **persistent synthesis**: the system should accumulate understanding over time instead of re-deriving it from raw chunks on every query. citeturn6search4turn4view1turn3view3turn31search1turn31search2

Enhanced RAG, however, has moved far beyond naïve vector search. GraphRAG, RAPTOR, Self-RAG, Corrective RAG, Adaptive-RAG, query rewriting, contextual retrieval, retrieval-time reranking, and meta-knowledge summaries all target parts of the same problem space: multi-hop reasoning, long-document understanding, retrieval precision, and evidence quality. In other words, many of the weaknesses Karpathy identified in baseline RAG are now at least **partially addressed** in the best modern RAG stacks. citeturn15search0turn15search1turn15search2turn15search3turn18search0turn18search1turn18search3turn19search0turn20search0turn17search8

What enhanced RAG still does **not** fully solve is the need for a durable, human-legible, reviewable synthesis layer: a place where contradictions are surfaced, earlier answers are preserved, project memory compounds, and good analyses become reusable artefacts instead of disappearing into chat logs. That is the strongest case for LLM Wiki. Karpathy’s own design explicitly files answers, comparisons, and analyses back into the wiki, and the most serious community extensions add lifecycle, review, git history, confidence, and memory management for exactly this reason. citeturn3view2turn3view3turn10view0turn12view0turn33view0turn33view1

The most credible recent comparative evidence points towards **complementarity rather than a single winner**. A systematic benchmark comparing RAG and GraphRAG finds that standard RAG tends to do better on detail-oriented factual QA, while GraphRAG tends to help more on multi-hop and corpus-level reasoning; the same study reports that hybrid selection and integration strategies can improve performance further. That pattern generalises well to this question: **pure LLM Wiki beats baseline RAG in some longitudinal knowledge-work settings, but hybrid Wiki + enhanced RAG is the best overall strategic direction**. citeturn24view0turn37view2turn37view3

For MCP-Geo, the recommended first prototype is therefore **not** a wiki-only system and **not** an “anti-RAG” design. It is a **review-gated synthesis layer on top of immutable repo-backed sources, combined with enhanced RAG over both the wiki and the raw corpus**. In a public-sector context, that prototype must be local-first or approved-environment first, fully versioned, citation-forward, auditable, and governed under current UK guidance on AI use, data protection, cyber security, and algorithmic transparency. citeturn28search4turn28search1turn28search2turn29search3turn29search18

## Terminology and source of truth

Karpathy originally framed the idea on X as **“LLM Knowledge Bases”**, describing a workflow in which LLMs build and query personal research knowledge bases that can reach roughly 100 articles and about 400,000 words. He then published the canonical architecture note as a GitHub Gist titled **“LLM Wiki”**, explicitly calling it “a pattern for building personal knowledge bases using LLMs” and an “idea file” intended to be copied into an agent workflow. For this report, **LLM Wiki** is the canonical pattern name, because it is the title of the primary architecture document, while **LLM Knowledge Bases** is best treated as the earlier framing or umbrella label. citeturn31search1turn31search2turn6search4

Karpathy’s primary architecture has three layers. The first is **immutable raw sources**: articles, papers, images, and data files that the LLM reads but never edits. The second is **the wiki**: markdown pages owned by the LLM, including summaries, entity pages, concept pages, comparisons, overviews, and syntheses. The third is **the schema**: an instruction file such as `CLAUDE.md` or `AGENTS.md` that tells the agent how the wiki is structured and how ingest, query, and maintenance should work. citeturn4view1turn4view2

The operating model is equally specific. **Ingest** means reading a new source, discussing it, writing a source summary, updating relevant concept and entity pages, updating the index, and appending to a chronological log. **Query** means searching the wiki first, synthesising an answer with citations, and optionally filing that answer back into the wiki as a new page. **Lint** means periodically checking for contradictions, stale claims, orphan pages, missing concept pages, broken cross-references, and gaps worth investigating further. The two special navigation files are `index.md`, which is content-oriented, and `log.md`, which is chronological and append-only. citeturn3view3turn3view4

The intended domains are broad but coherent: personal research, self-tracking, books, team and business knowledge, meeting transcripts, customer calls, competitive analysis, due diligence, trip planning, and any task where knowledge **accumulates over time**. Karpathy’s critique of RAG is also narrower and more precise than many secondary summaries suggest: baseline RAG re-discovers knowledge from scratch on each question, does not naturally accumulate synthesis, handles contradictions weakly, and lacks a persistent middle layer between the user and the raw corpus. citeturn4view1turn3view2

A useful source-of-truth hierarchy for this topic is therefore: first, Karpathy’s own X post and gist; second, implementation repositories and product documentation that actually expose code, architecture, and operations; third, academic papers that provide adjacent or comparative techniques; and only then secondary explainers, vendor blogs, and commentary. That distinction matters because many products now market themselves as “anti-RAG” or “agentic wiki” tools, but not all of them actually implement Karpathy’s three-layer pattern. citeturn6search4turn8view0turn24view0

## Prior-work map

The community moved quickly from idea to implementation. The closest thing to a reference implementation is the open-source `llmwiki` project and the hosted `llmwiki.app`, which mirror Karpathy’s three-layer model, expose an MCP server to Claude, support wiki writes with citations, and keep raw sources separate from generated wiki pages. This is an **implementation** and also a **hosted product**, because the code repository and running application line up. citeturn9view1turn9view2turn8view5

Several projects push the pattern towards **local-first, reviewable knowledge work**. `obsidian-llm-wiki-local` adds draft review, rejection feedback loops, selective recompilation, git commits, local model options including Ollama, and explicit vault structure for sources, drafts, index, and log. That is important because it operationalises one of the main missing pieces in Karpathy’s original note: a controlled publication path from LLM-authored draft to human-approved wiki page. citeturn10view0turn10view1turn10view3turn10view4

A second cluster turns the pattern into **wiki-backed retrieval**. `LLM Wiki Bridge` compiles a markdown vault into a concept graph that an agent queries directly through MCP. Its own description makes the distinction explicit: markdown stays the source of truth, the compiler turns that structure into a graph, and the agent answers by calling search and read tools “with evidence”, not by free-form paraphrase. This is closer to **hybrid Wiki + RAG** than to a pure prose-maintained LLM Wiki. citeturn35view1turn35view2turn35view3

A third cluster extracts the deterministic mechanics out of the agent and leaves the LLM to do semantic work. `Sparks` positions itself as a runtime for the “mechanical integrity” of a knowledge base, splitting deterministic tasks such as hashing, indexing, archiving, orphan detection, and commits from semantic tasks such as synthesis and contradiction spotting. That move is architecturally significant: it suggests the best long-term form of LLM Wiki may be **an agent-maintained knowledge layer plus a deterministic runtime**, rather than a single giant prompt file. citeturn33view0

Other recent implementations broaden the ingest surface or the domain. `llm-wiki-kit` adds PDFs, web pages, and YouTube transcripts under an MCP server; `llmwiki` by Pratiyush turns AI session logs into an interlinked wiki with machine-readable exports; `LLM Wiki Compiler` extends the idea to codebases and makes strong, self-reported efficiency claims; `Agentic Wiki Builder` experiments with git branches per ingest session for provenance. These are valuable as **implementation evidence**, but they should not be treated as independent proof of effectiveness. citeturn34view0turn34view1turn8view4turn8view6turn8view3

The most important **academic analogues** predate Karpathy’s gist. GraphRAG extracts entities, relationships and claims from unstructured text, performs community detection, and generates multi-level summaries and reports; RAPTOR recursively clusters and summarises chunks into a retrieval tree; MemoryBank, MemGPT, and the generative-agents literature contribute long-term memory, reflection, and retention ideas; and recent agent-memory systems explicitly add lifecycle, confidence, and semantic/episodic separation. Karpathy’s novelty is therefore not that persistent knowledge layers were unheard of, but that he turned several adjacent ideas into a very practical markdown-first agent workflow. citeturn37view1turn15search1turn23search0turn22search1turn22search2turn12view0

One caution is necessary. Some vendors and commentators immediately cast the pattern as **“RAG is dead”** or “the anti-RAG”. That is a marketing claim, not a settled technical conclusion. The more careful benchmark evidence points instead to complementarity and hybrid integration, especially once GraphRAG and other enhanced retrieval methods are included rather than only baseline vector RAG. citeturn6search22turn24view0

The core architectural distinction is between **answer-time synthesis** and **ingest-time synthesis**. Baseline and even much enhanced RAG remain primarily answer-time systems. LLM Wiki moves part of the synthesis effort to ingest and maintenance time. The hybrid model does both, which is why it is the most promising choice for MCP-Geo. citeturn3view2turn15search0turn15search1turn24view0

## Enhanced RAG strategy section

Enhanced RAG deserves to be treated as a serious comparator because several of its strongest forms now solve parts of the exact problem that LLM Wiki was proposed to solve. GraphRAG is the closest academic cousin: it performs ingest-time extraction of entities, relationships and claims, generates community summaries and reports, and then offers local, global and DRIFT search modes. RAPTOR does something similar without an explicit graph, using recursive chunk clustering and summarisation to create a multi-level retrieval tree. Both approaches are, in effect, **compiled intermediate knowledge layers**, even though they are usually described as RAG systems. citeturn37view1turn37view2turn37view3turn15search0turn15search1

Other enhanced RAG methods focus on **retrieval control**. Self-RAG learns when retrieval is needed and critiques its own outputs; Corrective RAG evaluates retrieval quality and can branch into corrective actions; Adaptive-RAG routes by query complexity; IRCoT and FLARE interleave reasoning and retrieval over multiple steps; and query rewriting improves the match between user intent and retriever behaviour. These techniques directly address Karpathy’s complaint that raw RAG keeps doing brittle, expensive synthesis from weakly matched chunks. citeturn15search2turn15search3turn18search0turn18search1turn18search3turn19search0

A further family improves **index quality rather than control flow**. Anthropic’s contextual retrieval adds chunk-specific explanatory context and reports large reductions in retrieval failure, especially when combined with reranking. Meta-knowledge methods generate metadata, synthetic QA, and summary objects before query time. Local hybrid tools such as `qmd` combine BM25, vector search, HyDE-style query paths, reciprocal-rank fusion, and reranking in one retriever. These are not persistent syntheses in Karpathy’s sense, but they substantially reduce one of the classic reasons for adopting a wiki layer: poor chunk recall. citeturn20search0turn20search11turn17search8turn36view0

Even so, some problems remain hard for RAG after enhancement. The first is **persistent synthesis ownership**: which answer, comparison, or interpretation should become part of the lasting knowledge base? The second is **contradiction as a maintained state**, not just a query-time nuisance: which claim has been superseded, what evidence changed it, and what is still unresolved? The third is **project memory**: meetings, decisions, design alternatives, and cross-session reasoning that need to accumulate into human-readable artefacts. Enhanced RAG can retrieve and verify those materials, but it does not naturally create or maintain the enduring synthesis layer unless one is added explicitly. citeturn3view3turn12view0turn33view1

That distinction helps answer the headline question. If the question is whether LLM Wiki is more effective than **baseline RAG**, the answer is often yes for longitudinal knowledge work. If the question is whether it is more effective than **state-of-the-art enhanced RAG**, the answer is no in general. Enhanced RAG now overlaps significantly with LLM Wiki on retrieval quality and multi-hop reasoning. What remains distinctive about LLM Wiki is **durable knowledge curation** rather than retrieval sophistication. citeturn3view2turn15search0turn15search1turn24view0

## Evaluation design

The right evaluation is a **four-way comparison**: baseline RAG, enhanced RAG, pure LLM Wiki, and hybrid Wiki + RAG. Baseline RAG should be a competent lexical-plus-vector system, not a straw man. Enhanced RAG should include at minimum hybrid retrieval, reranking, query rewriting, and one ingest-time compilation method such as RAPTOR or GraphRAG. Pure LLM Wiki should implement Karpathy’s three-layer pattern with index, log, answer filing, and lint. The hybrid should answer from the wiki and verify against raw sources or fresh slices before final output. citeturn21search0turn15search0turn15search1turn19search0turn20search0

The corpora should mix public benchmarks and MCP-Geo-specific material. For **multi-hop synthesis**, use MultiHop-RAG, which was built specifically because existing RAG systems underperform on queries requiring evidence across multiple documents. For **long-document understanding**, use QuALITY. For **meeting and transcript knowledge**, use QMSum and ODSum-meeting, both of which stress locating and summarising evidence across long conversational material. For **real project memory**, build an MCP-Geo corpus from documentation, ADRs, design notes, research notes, issue history, release notes, and meeting transcripts. citeturn25search3turn32search0turn26search0turn26search2

A dedicated **synthetic contradiction corpus** is essential. The cleanest design is to generate controlled source bundles around the same entities, concepts, or programme decisions, then inject changes across time: supersessions, near-duplicates, date shifts, policy reversals, ambiguous aliases, deliberate factual conflicts, and partial retractions. Each example should have gold annotations for: current best-supported claim, superseded claim, unresolved contradiction, and the source set needed to justify the decision. This is the task family in which pure LLM Wiki and hybrid models should outperform plain RAG if their claimed advantages are real.

The metrics should separate **retrieval, grounding, synthesis, and operations**. Answer factuality should use task-appropriate gold metrics plus human review. Citation precision should measure whether a cited passage actually supports the claim it is attached to. Citation recall should measure whether answer claims have supporting citations at all. Synthesis quality should be rated by reviewers for completeness, coherence, decision usefulness, and explicit handling of uncertainty. Contradiction handling should score detection, supersession accuracy, and abstention when evidence remains unresolved. Maintenance cost should include ingest tokens, query tokens, wall-clock latency, and reviewer minutes. Auditability should test whether an answer can be reproduced from a corpus snapshot and a commit hash. Human review burden should track how much draft material requires intervention before publication. Evaluation aids such as RAGAS, ARES and RAGChecker are useful, but they should be used as diagnostics rather than as the only arbiter. citeturn27search0turn27search1turn27search2

The experimental protocol should also be **time-aware**. Freshness tasks should hold out late-arriving documents such as recent release notes or policy updates, then test whether each architecture uses or ignores them. Pure LLM Wiki will tend to fail if the new material has not been ingested yet; baseline and enhanced RAG will tend to do better if the raw index is current; the hybrid should perform best if it consults the wiki for accumulated context but checks current raw material before finalising an answer. citeturn3view3turn24view0

Finally, do not rely only on LLM judges for comparative summarisation. Recent benchmark work shows meaningful position bias in LLM-as-a-judge settings when comparing RAG and GraphRAG summaries. Human blind review, randomised system order, and support packs showing cited evidence are necessary if MCP-Geo wants a trustworthy result rather than a convenient one. citeturn24view0

## Risks and failure modes

Pure LLM Wiki has three major failure modes. The first is **silent synthesis drift**: pages can become smoother and more coherent while actually moving further from the source record. The second is **authority laundering**: a wiki page can look definitive even when it is a low-confidence synthesis or an outdated interpretation. The third is **maintenance scaling**: Karpathy’s own note says the simple index-first approach works surprisingly well at moderate scale, but community extensions quickly moved towards search, lifecycle, review, and graph tooling, which is a sign that the original pattern needs augmentation as it grows. citeturn3view3turn12view0turn33view0

Enhanced RAG has a different risk profile. It is strong on freshness and current lookup, but it can still miss key evidence, overfit to the retriever’s scoring function, or drown answers in redundant fragments. Graph-based systems add their own failure surfaces, including entity-linking errors, graph-construction skew, and summary layers that become too corpus-level to answer detail-specific questions. Recent comparative work also finds non-trivial cost, latency, and storage penalties for GraphRAG-style systems, alongside the risk that global summaries lose query-specific detail. citeturn24view0turn16search14turn37view2

Hybrid systems reduce some errors but introduce **systems complexity**. If the wiki and the raw corpus disagree, the system needs a principled conflict policy. If the wiki cites the source corpus but the retriever prefers a newer uncited fragment, the answering layer needs a clear rule for supersession and a way to expose uncertainty. Without that, the hybrid can become the worst of both worlds: expensive, difficult to audit, and hard to explain.

For public-sector use, governance failures matter as much as model failures. The UK AI Playbook emphasises safe, effective and secure deployment across government; the ICO’s AI and data-protection guidance stresses lawful, fair and transparent processing of personal data; and the NCSC’s secure-AI guidance frames risks across design, development, deployment, and operation. For MCP-Geo that means source classification, minimisation of personal data, approval boundaries, secure runtime design, and logs that show who changed what and why. citeturn28search4turn28search7turn28search1turn28search9turn28search2turn28search13

Transparency is also not optional once the system enters decision support. The Algorithmic Transparency Recording Standard enables public-sector bodies to publish how and why algorithmic tools are used; in central government it is part of the mandatory policy for covered organisations, and it is available more broadly as recommended practice. If MCP-Geo’s knowledge system materially informs public decisions, evidence triage, or operational prioritisation, an ATRS-style record and internal control documentation should be prepared from the outset rather than retrofitted later. citeturn29search3turn29search18turn29search0

The final limitation is evidential. Community LLM Wiki implementations are **extremely recent**. There is already meaningful implementation evidence, but very little independent benchmarking specific to “LLM Wiki versus enhanced RAG” as a category. The strongest current conclusion is therefore architectural and comparative, not yet the result of multiple mature production studies.

## Recommendation for MCP-Geo

MCP-Geo should **prototype a hybrid architecture first**. The right question is not “wiki or RAG?” but “where should persistent synthesis live, and how should it be checked against raw evidence?” Karpathy’s pattern is strongest when the same body of material is revisited for weeks or months and the real value lies in accumulating synthesis, comparisons, questions, and contradictions. Enhanced RAG is strongest when the need is fresh, high-recall, current retrieval over large or fast-changing corpora. MCP-Geo almost certainly needs both. citeturn4view1turn24view0turn20search0

The recommended first prototype is this. Keep **repo files as the canonical source of truth**: documents, notes, release notes, ADRs, transcripts, and research artefacts remain immutable or explicitly versioned. Preserve the current Obsidian descriptive catalogue, but add a new **LLM-maintained synthesis layer** as a separate part of the vault. That layer should contain source summaries, concept pages, entity pages where appropriate, comparison pages, overview pages, and saved answers to recurring analytical questions. It should also have explicit `index.md`, `log.md`, and draft/publication states. citeturn4view1turn3view3turn10view0

At query time, the agent should use a **two-pass policy**. First, consult the synthesis layer to exploit accumulated knowledge and project memory. Second, verify the answer against the raw corpus using enhanced retrieval, ideally hybrid lexical/vector search with reranking and optional graph or hierarchical retrieval for multi-hop tasks. This can be implemented with an existing local search layer such as `qmd`, a GraphRAG-style component for selected corpora, or a modest custom retrieval layer over the repo. The key design rule is that **approved raw evidence outranks wiki prose when they conflict**, unless a reviewed supersession record exists. citeturn36view0turn37view2turn37view3

That recommendation resolves the open decisions as follows. **The existing Obsidian knowledge base should remain the descriptive catalogue, but it should gain an LLM-maintained synthesis layer.** **The source of truth should remain repo files, not the wiki itself.** The wiki should be a first-class **derived artefact**, not the authoritative record, unless a specific page has passed a human promotion gate and is explicitly marked as a reviewed briefing or decision note. **The first prototype should be a minimal local harness**, adapting the current `build_obsidian_kb.py` approach and borrowing ideas from the stronger open implementations, rather than adopting a hosted product as the foundation. That minimises procurement, security, and governance risk while making the evaluation cleaner. citeturn10view0turn35view1turn33view0turn34view0

An existing implementation can still accelerate the prototype, but as a **reference**, not as the platform of record. `obsidian-llm-wiki-local` is useful for ideas around draft review and git-based publication. `LLM Wiki Bridge` is useful for vault-to-graph retrieval patterns. `Sparks` is useful for separating deterministic mechanics from semantic work. `llmwiki` is useful as a reference for a full three-layer implementation. In practice, MCP-Geo is likely to benefit more from a small local harness with explicit control points than from trying to adopt one community project wholesale. citeturn10view0turn35view1turn33view0turn9view1

The mandatory governance controls are straightforward. Every LLM-authored synthesis page should begin life as a **draft**. Promotion to reviewed status should require: source-linked citations to raw evidence; a corpus snapshot or commit hash; a staleness check against recent documents; contradiction review where conflicts exist; reviewer identity and timestamp; and a classification check for sensitive content. The system should keep audit logs for ingest, edits, deletions, draft approvals, and query outputs. Personal data should be minimised, and sensitive or secret material should be filtered before synthesis where possible. If the system is used in formal public decision support, internal control documentation and ATRS-aligned transparency records should be prepared. citeturn28search1turn28search2turn29search3turn29search18

When should MCP-Geo use LLM Wiki? Use it for **accumulating, interpretive, longitudinal work**: research tracking, policy landscape synthesis, recurring comparisons, release-history interpretation, meeting-memory distillation, and project onboarding. When is enhanced RAG enough? Use it for **fresh, factual, high-churn lookup** where persistent synthesis adds little value. When should the two be combined? Combine them whenever users need both **durable understanding and current verification**. For public-sector knowledge work, that combined mode should be the default rather than the exception. citeturn4view1turn20search0turn24view0

Open questions remain. This report does not include MCP-Geo’s private corpus, existing scripts, or internal constraints such as hosting policy, data classification patterns, or current release workflows. Those will affect the final engineering design. But they are unlikely to change the main conclusion: **MCP-Geo should prototype a review-gated hybrid, not choose between pure wiki and pure RAG as if they were mutually exclusive.**
