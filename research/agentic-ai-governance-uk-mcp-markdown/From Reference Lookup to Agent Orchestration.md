## Executive summary

Software development has not simply become “AI coding”; it has moved through a sequence of distinct operational modes. The centre of gravity has shifted from **retrieval** of information, to **prediction** in the editor, to **dialogue** with a coding assistant, to **delegated execution** by local and cloud agents, and now toward **orchestration** of multiple agents, tools, contexts, and review gates. In that progression, the developer’s bottleneck moves from remembering syntax, to framing tasks well, to supervising parallel work, to verifying that outputs are correct, safe, and worth merging. Official product documentation now explicitly describes agents that read repositories, edit multiple files, run commands, use MCP-connected tools, open pull requests, and work in parallel in cloud environments. [source map](agentic-ai-coding-source-map.md)

The metaphors people use have evolved with the tooling. Documentation-and-search-era coding was often understood as craft, investigation, or apprenticeship. IDE assistance invited metaphors such as power tools, instrumentation, spellcheck, and compiler-adjacent safety rails. Copilot-style completion popularised the “AI pair programmer” metaphor. Chat-based assistants were described as tutor, rubber duck, consultant, or “Stack Overflow on demand”. IDE-native agents pushed the metaphor toward junior developer, apprentice, or mechanic. Cloud agents introduced contractor, build farm, and ticket factory metaphors. Multi-agent systems are now producing commander, conductor, newsroom editor, air-traffic control, and RTS metaphors. Some of these are merely rhetorical status upgrades for tools that still need constant supervision; others genuinely predict useful working habits. [source map](agentic-ai-coding-source-map.md)

The strongest evidence is that **assistance is not the same as autonomy**, and **autonomy is not the same as trustworthiness**. Vendor and benchmark claims show real upside in some settings: GitHub’s controlled Copilot experiment reported a 55.8% faster completion time on a bounded programming task, and GitHub’s later enterprise studies reported self-reported and observational improvements in some organisational contexts. But a randomised controlled trial by METR on experienced open-source developers working in their own familiar repositories found the opposite headline result: AI assistance made them **19% slower on average**, despite users expecting a speed-up. This is not a contradiction so much as a warning that the effect size depends heavily on task shape, codebase familiarity, verification burden, and the hidden time spent on review, correction, and context assembly. [source map](agentic-ai-coding-source-map.md)

That is why the most useful contemporary metaphor is not “AI as senior engineer” but **AI as a stack of differently reliable collaborators**, each demanding a different management style. The RTS metaphor becomes genuinely predictive only when teams are assigning multiple concurrent tasks to different agents, watching progress at multiple levels of abstraction, trading off latency against quality and cost, and repeatedly pulling work back through quality gates. In that world, the human developer is less a typist and more a **mission commander, scheduler, reviewer, and risk owner**. Verification therefore becomes more central, not less. Official and research sources now converge on that point: agentic throughput expands faster than unaided human review capacity, which creates what Sonar calls a “verification gap”, and what formal-methods advocates describe as a need for evidence that is independent of the model that wrote the code. [source map](agentic-ai-coding-source-map.md)

## Timeline and taxonomy of coding-assistance modes

The broad timeline is now clear. Search and Q&A externalised memory and normalised “programming by retrieval”; IDE assistance externalised syntax and some semantics into the editor; autocomplete externalised local continuation; chat assistants externalised explanation and example generation; IDE-native agents externalised multi-file editing and local iteration; cloud agents externalised long-running implementation to remote sandboxes; multi-agent systems externalise **parallelism itself**. Official product materials from GitHub, Anthropic, OpenAI, Google, Cursor, JetBrains, Sourcegraph, Replit, and Cognition all document this shift from suggestion to delegated execution and then to orchestration. Several broad evaluative patterns emerge. As tools become more agentic, **autonomy, context requirement, verification burden, and cost volatility all rise**. Latency gets longer per task, but human wall-clock time may fall if delegation is well chosen. Greenfield projects are generally more forgiving than legacy systems unless the repo has strong documentation, rules, tests, and retrieval. Security risk increases sharply at the moment agents gain command execution, external tool access, or cloud-side write permissions. Learning value for junior engineers is highest in the search, IDE, and chat modes, and becomes ambiguous once the system is doing large chunks of work that the junior would otherwise have had to reason through. GitHub’s controlled productivity study and METR’s real-repo study together strongly suggest that “AI helps” is too coarse a statement; the real question is **which mode on which task under which review discipline**. But once you have **parallel worktrees, background runs, recurring automations, MCP tools, cloud branches, remote PRs, and custom skills**, the more realistic question is no longer “What prompt should I give my pair?” but “How do I run my economy, prioritise tasks, preserve visibility, and verify outputs faster than I generate them?” That is where the RTS metaphor earns its keep. ## RTS mechanics mapped to agentic coding

RTS scholarship and design writing describe the genre in terms of resource gathering, base building, technological development, incomplete information under fog of war, scouting, build-order optimisation, map control, and interface elements such as the minimap and HUD. Those concepts provide a disciplined vocabulary for agentic coding, provided the mapping is treated as a heuristic rather than a literal model of software engineering. ## What the RTS metaphor gets right and wrong

What it gets right is mostly operational. First, it captures the way agentic programming turns **parallel task allocation** into a first-order skill. Official tooling now supports multiple concurrent tasks, background execution, worktrees, subagents, and asynchronous sessions. That means developers increasingly win or lose on decomposition, sequencing, and interruption handling, not just on typing speed or API recall. [source map](agentic-ai-coding-source-map.md)

Second, it captures **fog of war** better than the older “intern” metaphor. The biggest current failure mode is not usually that an agent cannot produce plausible code. It is that the system lacks some buried institutional or architectural fact, and neither the agent nor the human noticed the omission in time. Anthropic, Cursor, Devin, and OpenAI all now emphasise rules, skills, memory, configuration, and context engineering precisely because raw model capability is not enough. [source map](agentic-ai-coding-source-map.md)

Third, it captures **economy management**. The visible spend is model usage, but the true economy includes CI minutes, tool quotas, review capacity, merge queue congestion, and defect risk. That is why outcome metrics are more important than vanity measures such as token burn or agent count. Both Sonar’s survey work and Stack Overflow’s survey work show a widening adoption-trust gap: many developers use AI heavily, while a large share still distrust its accuracy and fail to verify consistently. [source map](agentic-ai-coding-source-map.md)

What it gets wrong is just as important. RTS games are usually **adversarial, bounded, instrumented, and resettable**. Software engineering in organisations is collaborative, open-ended, partially uninstrumented, and path dependent. The enemy is rarely another player; it is usually ambiguity, weak requirements, institutional constraint, or accumulated complexity. The RTS frame also tempts people to valorise tempo over comprehension. That is dangerous, because software failures are not harmless unit losses: they become outages, vulnerabilities, procurement breaches, or public harms. NCSC and UK government guidance both stress secure design, secure development, governance, and accountability in AI systems; those are not optional “macro” choices but core operating constraints. [source map](agentic-ai-coding-source-map.md)

The metaphor also breaks when people import the wrong social assumptions. Calling an agent a “staff engineer” or a “swarm” can smuggle in unwarranted trust. Current agents can appear organised, but that does not mean they possess stable product judgment, legal awareness, or an instinct for not making damaging local optimisations. Research on automation bias and cognitive bias in developer–LLM interaction suggests that fluent systems can increase over-reliance even when they do not improve ground-truth performance. The RTS metaphor is helpful only if it keeps the human accountable for intent, acceptance, and safety. [source map](agentic-ai-coding-source-map.md)

The most practical conclusion is therefore this: the RTS metaphor is **predictive for coordination**, **weak for trust**, and **dangerous for quality unless paired with a verification metaphor**. “RTS commander” explains how work gets allocated. “Court of law” or “laboratory assay” explains how work gets accepted. One without the other produces exactly the pathology many teams are already reporting: AI causes code volume to rise faster than review discipline. [source map](agentic-ai-coding-source-map.md)

## Operating model, governance, and metrics for an RTS-style agentic programmer

A workable operating model begins before any agent runs. The repository must be prepared so that humans and tools are both able to navigate it. In practice that means a clear test entry point, deterministic linting and formatting, reproducible dev environments where possible, visible ownership, architecture notes close to code, and persistent instructions through rules, memory files, or skills. Product docs from Anthropic, Cursor, Codex, Devin, and Junie all converge on this need for explicit project-level guidance and reusable procedures. [source map](agentic-ai-coding-source-map.md)

A sensible daily workflow is then cyclical rather than heroic. Start by triaging work into **direct execution**, **delegable bounded tasks**, and **high-risk tasks requiring specification first**. Use one planning pass to scout the repo and identify hidden dependencies. Only then allocate agents. Good decomposition tends to use small, reviewable units: “write failing property tests for parser invariants”, “draft migration script and rollback notes”, “produce a plan for splitting this module”, “repro and isolate the CI failure”, “prepare docs for endpoint changes”. This is much closer to queue discipline than to free-form prompting. Cursor’s plan mode, Ask Devin, Copilot planning, and Anthropic’s best-practice guidance all push in that direction. [source map](agentic-ai-coding-source-map.md)

Monitoring should happen at two levels simultaneously. At the **local tactical level**, inspect logs, diffs, terminal commands, and failing tests. At the **dashboard level**, track which tasks are active, blocked, awaiting approval, or likely to collide in merge. This is the genuine “minimap” part of the RTS analogy. The operator’s job is not constant typing; it is noticing when a session is drifting, when two agents are converging on the same file set, or when a cheap exploratory task is consuming expensive review bandwidth for little expected value. [source map](agentic-ai-coding-source-map.md)

Interruption discipline matters. Developers should stop or re-scope agents when any of the following appear: edits radiate beyond the intended file or service boundary; the agent starts writing speculative architecture without explicit instruction; command sequences require elevated permissions; CI failures multiply rather than narrow; or the diff becomes too large to review with confidence. Anthropic and GitHub both emphasise approval gates and permissions; Cognition, Cursor, and Jules similarly foreground controlled environments and visible progress. Least privilege is not bureaucratic drag here; it is the operational equivalent of not giving every worker unit the keys to the entire base. [source map](agentic-ai-coding-source-map.md)

Verification and merge strategy should be stricter than in pre-agent workflows, not looser. The right pattern is “generate cheaply, accept expensively”. Require at least one independent evidence source before merge: deterministic tests, property tests, static analysis, security scanning, proof obligations where relevant, or targeted manual review against specification. Sonar’s AI Code Assurance, NIST’s SSDF, NCSC’s secure-AI guidance, and current thinking on formal verification all point in the same direction: the acceptance pipeline must not rely on the same generative system both creating and certifying the change. [source map](agentic-ai-coding-source-map.md)

Cost controls should therefore be tied to outcomes, not mere utilisation. Use cheaper models for reconnaissance and drafting; reserve premium reasoning models for plans, hard bugs, or security-sensitive changes. Put budgets around background tasks, bound concurrent sessions by actual review capacity, and expire stale branches aggressively. OpenAI, GitHub, Cursor, Jules, and Anthropic all now expose configuration, models, plans, or background modes that make this sort of economic discipline possible. [source map](agentic-ai-coding-source-map.md)

The metrics should follow the same logic. Raw agent activity is mostly vanity. Better measures are those that preserve the distinction between output, accepted value, and downstream quality.

| Metric | Why it matters | Why it is better than vanity metrics |
|---|---|---|
| Accepted pull requests per engineer-week | Measures value that survived review and integration | Rejects the illusion that generating more diffs equals more progress |
| Lead time for accepted change | Captures end-to-end delivery including review and merge friction | Better than “time to first draft” because it includes verification and coordination |
| Escaped defects and rollback rate | Tests whether speed is simply pushing problems downstream | Critical counterweight to high-volume generation |
| Review cycles per PR | Indicates whether agent output is actually mergeable | Better than token counts because it exposes hidden review cost |
| Test coverage improvement on changed code | Measures evidence added, not just code emitted | Aligns with verification-led adoption |
| Security findings per accepted change | Helps catch the risk that AI amplifies insecure patterns | Better than “number of scans run” because it ties to accepted output |
| Maintainability deltas on changed code | Watches for verification debt and long-term cost | More useful than short-term velocity anecdotes |
| Cost per accepted change | Connects model spend to outcomes | Better than raw token burn because it respects task shape and value |
| Duplicate-work rate across agents | Measures orchestration quality | Reveals bad decomposition or poor dashboarding |
| Human review minutes per accepted change | Shows whether the “economy” is healthy | Exposes when agent output is simply converting writing time into review time |

These outcome-focused metrics align with both contemporary secure-development frameworks and the emerging evidence that success in agentic coding depends on managing verification and trust, not just throughput. [source map](agentic-ai-coding-source-map.md)

## Implications and final synthesis

For **senior engineers**, the job becomes more managerial in the best and worst senses. Their comparative advantage shifts toward scoping, architectural judgment, risk recognition, context engineering, and evidentiary acceptance. They are likely to gain leverage fastest, but they are also the group most likely to create invisible governance problems if they normalise high-autonomy workflows without robust review discipline. Stack Overflow’s survey data suggests experienced developers are also the least trusting of AI output, which is probably healthy. [source map](agentic-ai-coding-source-map.md)

For **junior engineers**, the picture is double-edged. AI can accelerate onboarding, explanation, and exploration, and tools such as Ask Devin, Cody, Copilot Enterprise, and code-understanding interfaces genuinely help with unfamiliar codebases. But if juniors mainly consume generated diffs without reconstructing the reasoning, they risk outsourcing the very cognitive work by which engineers become better. Research on human–AI collaboration and cognitive bias should be taken seriously here. Juniors need deliberate practice in reviewing, testing, and explaining agent-written code, not just in steering agents to produce it. [source map](agentic-ai-coding-source-map.md)

For **engineering managers**, the transition is from tool procurement to workflow design. The hard questions are no longer “Which model is best?” alone, but “Which tasks are delegable?”, “Who approves what?”, “Where do rules live?”, “How much parallelism can we review?”, and “Which metrics tell us whether we are buying speed or merely moving the toil?” Multi-agent coding without merge and review governance is likely to produce a false sense of acceleration. [source map](agentic-ai-coding-source-map.md)

For **public-sector digital teams**, caution should be stronger still. UK government guidance, the AI Playbook, the Technology Code of Practice, and NCSC’s secure-AI guidance all point toward a disciplined approach centred on security, procurement clarity, accountability, and assurance. In practice that means careful data handling, clearly bounded use cases, auditable approval points, and explicit decisions about whether code or context may leave the organisation’s environment. For councils, departments, and arms-length bodies, the question is not whether agentic coding exists; it is whether the team can evidence that its use meets the same standards that would apply to any other development process. [source map](agentic-ai-coding-source-map.md)

For **regulated or safety-critical software**, the lesson is straightforward: generation can be agentic, but acceptance must be evidentiary. That means stronger use of static analysis, policy-as-code, reproducible builds, secrets controls, formal specifications where proportionate, and segregation between the system that proposes changes and the system that certifies them. Formal-verification work and security evaluations of AI-generated code do not justify panic, but they do justify refusing the fantasy that human review alone will scale indefinitely under agent-amplified code volume. [source map](agentic-ai-coding-source-map.md)

The final synthesis is that **no single metaphor is sufficient** for 2026-era agentic coding. The best composite model is:

**researcher + instrument pilot + editor + commander + judge**

That combination is better than “pair programmer”, “intern”, or “RTS commander” alone. The **researcher** metaphor preserves the need to interrogate sources and uncover hidden context. The **instrument pilot** metaphor reminds us that dashboards and tooling augment cognition but do not replace responsibility. The **editor** metaphor captures the ongoing reality that most AI output still requires shaping, pruning, and integration. The **commander** metaphor becomes accurate when several agents work in parallel and attention is the scarce resource. The **judge** metaphor is the crucial corrective: in the end, someone must decide whether the code is right, safe, lawful, maintainable, and worth the complexity it introduces. [source map](agentic-ai-coding-source-map.md)

The RTS metaphor is therefore neither hype nor complete theory. It is a good operational metaphor for the **orchestration layer** of modern coding, and a bad total philosophy of software engineering. Used properly, it teaches build order, scouting, economy, dashboards, and replay analysis. Used carelessly, it glamorises speed, hides verification debt, and mistakes visible activity for reliable progress. The most competent agentic programmers in 2026 will be the ones who learn to play both games at once: the RTS of orchestration, and the courtroom of verification.
